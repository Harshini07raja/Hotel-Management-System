# Requirement-to-Component Mapping and System Design Justification

## 1. Overview
The **Scalable Hotel Management System** integrates eight core distributed system-design components directly into the business workflows of a full-scale hotel reservation and operations platform. Every component addresses a specific architectural, performance, or scalability requirement.

## 3. Distributed Concurrency & Booking Consistency Architecture
The most critical requirement in hotel reservation systems is **double booking prevention**:
1. **Half-Open Date Interval**: Bookings occupy nights from `checkIn` (inclusive) to `checkOut` (exclusive). Two reservations $[A_{in}, A_{out})$ and $[B_{in}, B_{out})$ overlap if and only if:
   $$A_{in} < B_{out} \quad \text{and} \quad A_{out} > B_{in}$$
2. **Authoritative Shard Execution**: Every room and its reservations belong strictly to the shard identified by `hash(hotelId)`. All booking attempts for rooms in that hotel execute on that shard.
3. **Atomic Conditional Concurrency**:
   - At the database level, room reservation status and overlapping booking records are checked atomically using optimistic locking / conditional updates (`findAndModify` with booking collision criteria).
   - Redis locks are used strictly as a fast-fail pre-filter, while the database shard conditional update provides the **final, authoritative correctness guarantee**.
4. **Idempotency Keys**:
   - Clients supply an `Idempotency-Key` header (or UUID). Retrying a failed network request returns the identical booking response without reserving another room.
